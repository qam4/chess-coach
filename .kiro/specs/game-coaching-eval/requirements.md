# Requirements Document

End-to-end game-coaching eval — play a whole game and judge the coaching
across it.

## Introduction

Every coaching eval today runs on **isolated, curated positions** — the
position-explanation benchmark (`positions.yaml`) and the move-feedback
benchmark (`move_feedback.yaml`). That is the "position analyst" mode
VISION explicitly does not want to be, and it never exercises the coach
over the **natural arc of a real game** (opening → middlegame → endgame)
on the positions a player actually reaches.

This feature drives a **whole game** — two Blunder engines playing at
chosen strengths — coaches the student side's moves with the real
pipeline, and has a **frontier judge (kiro-cli)** review the coaching
across the game. It is deliberately an **end-to-end test**: it exercises
the full stack (engine play → coaching protocol → local-LLM coach →
frontier judge) on realistic games, so it surfaces both integration
breakage and coaching-quality regressions that single positions miss.

It also builds the reusable **game-trajectory** substrate that the
cross-game progress tracker (VISION Step 2, separate spec) will consume.

Design agreed with the product owner:
- Players are **Blunder at a chosen Elo** — the student weak enough to
  make real, coachable mistakes; the opponent at a chosen level.
- The **coach's analysis engine stays full-strength** — the same binary
  serves three roles (student-weak player, opponent player, full-strength
  coach oracle) via separate instances / options.
- The judge is a **frontier model via kiro-cli** (`CliProvider`, already
  shipped). Using a frontier model to judge the local LLM is accepted as
  a proxy (honest ceiling per BACKLOG "Who calibrates teaching quality?")
  and is squarely within VISION's rule (a frontier model is allowed as an
  eval judge, never as the runtime coach).

Non-negotiables:
- **Reuse, don't rebuild.** Coaching uses the shipped `Coach.evaluate_move`
  (the move-feedback path); judging reuses the existing judge + the
  move-feedback rubric + `CliProvider`; long runs use kiro-monitor. The
  genuinely new code is the game driver + the trajectory model + game-level
  aggregation.
- **Coach oracle is always full strength.** The players' reduced Elo must
  never weaken the analysis the coach grounds its feedback on.
- **Offline/local except the sanctioned judge.** No project code, secrets,
  or data goes to a third party; the only external call is the eval judge
  the operator explicitly configures (kiro-cli), consistent with the
  existing eval harness.
- **Reproducible.** A run saves its full trajectory + verdicts and is
  re-runnable from a fixed seed / fixed engine settings.

## Glossary

- **Game trajectory** — a played game reduced to an ordered list of
  **turn records**, one per *student* move:
  `(ply, fen_before, student_move, engine_best, eval_before/after,
  eval_drop, classification, active_features, coach_feedback)`. The
  reusable substrate (also feeds the tracker).
- **Player engine** — a Blunder instance generating game moves at a set
  Elo (`UCI_LimitStrength`/`UCI_Elo`). One instance serves both sides,
  its Elo set per mover.
- **Coach oracle** — a *separate* full-strength Blunder instance the
  `Coach` uses for `get_comparison_report` / `get_position_report`.
- **Student side** — the color whose moves are coached and judged.
- **Coaching turn** — one student move + the coach's feedback on it.
- **Frontier judge** — the operator-configured kiro-cli provider that
  scores coaching against engine ground truth.
- **Per-move verdict** — the judge's rubric result for one coaching turn.
- **Game report** — per-turn verdicts + game aggregate + surfaced E2E
  issues, persisted to the run's output dir.

## Requirements

### Requirement 1: Play a full game between two leveled engines

**User Story:** As an evaluator, I want a whole game generated by Blunder
at chosen strengths, so the coach is tested on the real positions a player
of that level reaches.

#### Acceptance Criteria

1. THE driver SHALL play a full game from a start position (default the
   initial position; a supplied FEN allowed) using a player engine, setting
   the mover's Elo before each move from the configured **student** and
   **opponent** Elos (via `UCI_LimitStrength`/`UCI_Elo`).
2. THE game SHALL terminate on checkmate/stalemate/insufficient material/
   draw-by-rule OR a configurable **ply cap** (default e.g. 80), whichever
   comes first.
3. THE driver SHALL record, for every **student** move, a turn record with
   the fields in the Glossary; opponent moves advance the game but are not
   coached/judged.
4. THE student color SHALL be configurable (default: student plays White).

### Requirement 2: Coach the student moves with the real pipeline

**User Story:** As an evaluator, I want the actual production coaching path
exercised, so the eval reflects what a user would get.

#### Acceptance Criteria

1. FOR each student move, THE system SHALL produce coaching feedback via the
   shipped `Coach.evaluate_move` (the move-feedback path), grounded by a
   **full-strength coach-oracle** engine distinct from the player engine.
2. THE coach's engine settings (depth, guidance on/off, constrain_moves,
   template_only, model) SHALL be configurable so a run pins the exact
   coaching configuration under test.
3. THE reduced player Elo SHALL NOT affect the coach oracle's strength.

### Requirement 3: Judge the coaching across the game (frontier)

**User Story:** As an evaluator, I want a frontier model to check the
coaching against ground truth over the whole game, so I get a validity
signal the position benchmarks can't give.

#### Acceptance Criteria

1. FOR each coaching turn, THE system SHALL score the coaching feedback with
   the frontier judge (`CliProvider`) against the engine's ground truth for
   that move (the comparison report), reusing the move-feedback rubric.
2. THE judge provider/command/model SHALL be configurable exactly as the
   existing eval harness does (`--judge-provider cli`, `--judge-command`),
   and the judge SHALL default to disabled so a run can generate + record a
   trajectory without a judge (cheap smoke / tracker data).
3. A judge failure on one turn SHALL NOT abort the run — it is recorded as
   an un-judged turn (parallels the harness's per-item judge-error handling).
4. (v2, optional) THE system MAY add a **game-level** judging pass that sees
   the whole trajectory and assesses consistency, whether the coach caught
   the critical moments (`critical_moment`), and non-repetition. v1 is
   per-move judging only.

### Requirement 4: Trajectory data model (shared substrate)

**User Story:** As a developer, I want the played game captured as a
serializable trajectory, so it can be persisted, replayed, and consumed by
the cross-game tracker.

#### Acceptance Criteria

1. THE system SHALL define a serializable `GameTrajectory` (metadata +
   ordered `TurnRecord`s) with `to_dict`/`from_dict`, written to the run's
   output dir as JSON.
2. Each `TurnRecord` SHALL carry the engine ground truth (best move, evals,
   drop, classification) and the position's active features so a downstream
   consumer (the tracker) needs no re-analysis.
3. THE trajectory SHALL be replayable: given a saved trajectory, judging (or
   re-judging) SHALL be possible without replaying the engine game.

### Requirement 5: Game report + aggregation

**User Story:** As an evaluator, I want a per-game report I can read at a
glance and that surfaces problems.

#### Acceptance Criteria

1. THE run SHALL emit a report with: per-turn (ply, student move,
   classification, coaching quality if judged), a game aggregate (mean
   coaching quality, counts by classification, judged/un-judged counts),
   and any **E2E issues surfaced** (engine/coach/judge errors, illegal or
   empty coach outputs, pipeline exceptions).
2. THE report + the raw trajectory + verdicts SHALL be written to the
   configured output dir (like the other eval tools).
3. Objective fidelity checks already available (illegal/off-menu/placement
   via `check_coaching_fidelity`) SHALL be run per coaching turn and their
   counts included, so the report has a judge-free objective layer too.

### Requirement 6: Run mechanics

**User Story:** As an operator, I want to run this like the other eval
tools, including long unattended runs.

#### Acceptance Criteria

1. THE feature SHALL ship as a `scripts/` driver over a **pure `eval/`
   core** (game loop, trajectory, aggregation are unit-testable without a
   live engine/LLM via injected fakes), matching the other eval tools.
2. Config knobs SHALL include: student Elo, opponent Elo, start FEN, ply
   cap, number of games, coach config (depth/guidance/constrain_moves/
   template_only/model/base-url), judge provider/command/model, output dir,
   RNG seed.
3. THE driver SHALL be safe to launch under kiro-monitor (a game is
   ~20–40 coached moves; multiple games are minutes-to-tens-of-minutes).

### Requirement 7: Reproducibility

**User Story:** As an evaluator, I want a run to be reproducible so results
are trustworthy.

#### Acceptance Criteria

1. Engine play SHALL use fixed settings (depth/level) and an RNG seed where
   Blunder's skill adds noise, so a game is reproducible given the same
   seed + settings; the seed SHALL be recorded in the trajectory metadata.
2. THE judge SHALL run at temperature 0 (as `judge_response` already does).
3. Non-determinism that cannot be removed (a thinking judge, engine
   threading) SHALL be documented, not hidden.

### Requirement 8: Quality gates

**User Story:** As a maintainer, I want the feature to land green and
tested on its pure core.

#### Acceptance Criteria

1. `uv run pytest`, `uv run mypy src`, `uv run ruff check src tests
   scripts`, `uv run ruff format --check` SHALL all pass.
2. THE pure core (game loop over a fake engine, trajectory build/serialize,
   aggregation) SHALL be unit-tested without a live engine, LLM, or judge.
3. A tiny smoke (one very short game, judge disabled, fake or real local
   engine) SHALL exercise the driver end-to-end in CI-safe time.
